# M11-L03 · State
> Video: Module 11, Lesson 3. Watch it first, then follow along here.

## What you'll learn
- What state is: Terraform's **map from addresses in code to real object IDs**, with cached attributes and dependencies
- How `plan` uses state: refresh, then compare (in code not in state = create; different = update/replace; in state not in code = destroy)
- What's inside `terraform.tfstate` (`version`, `serial`, `lineage`, outputs, resources) and why it holds **secrets in plain text**
- Moving state to a **remote S3 backend** with versioning, encryption and **S3-native locking** (`use_lockfile`)
- Seeing a lock block a second run, `force-unlock`, and the rule: **never edit state by hand** (use `moved`, `state mv`, `state rm`, `import`)
- Splitting state by environment and component to limit the blast radius

## Follow along
1. Look at local state in the lesson 1 project:
   ```bash
   cd ~/tf/hello
   ls -la; head -c 600 terraform.tfstate; echo
   ```
   You should see `terraform.tfstate` (6216 bytes in the video) and `terraform.tfstate.backup` (the previous version), then JSON:
   ```
   "version": 4,
   "terraform_version": "1.16.6",
   "serial": 6,
   "lineage": "c57244a7-...",
   "outputs": { "bucket_name": { "value": "allcs-media-dev-506c01", ...
   ```
   `serial` goes up with every change; `lineage` identifies this state for life. Do not edit this file.

2. Read state through Terraform instead:
   ```bash
   terraform state list
   terraform state show aws_s3_bucket_versioning.media
   ```
   ```
   data.aws_availability_zones.available
   aws_s3_bucket.media
   aws_s3_bucket_versioning.media
   random_id.suffix
   ```
   and the cached attributes (`bucket`, `region = "us-east-1"`, `mfa_delete = "Disabled"`, `status = "Enabled"`).

3. Secrets in state: open `examples/b04-data.tf` from this folder. With `manage_master_user_password = true`, RDS keeps the password in Secrets Manager and state only records the secret's ARN. (Since Terraform 1.11, write-only `_wo` arguments and ephemeral values also keep values out of state.)

4. Create a versioned state bucket (**free/pennies**; deleted at the end by `delete-state-bucket.sh`) and fill in `backend.tf`:
   ```bash
   STATE=allcs-tfstate-$RANDOM$RANDOM; aws s3api create-bucket --bucket $STATE --query Location --output text; aws s3api put-bucket-versioning --bucket $STATE --versioning-configuration Status=Enabled; echo $STATE > ~/state_bucket
   cp ~/Devops_Course/terraform/m11-l03-state/backend.tf . && sed -i "s/allcs-tfstate-CHANGE-ME/$(cat ~/state_bucket)/" backend.tf
   cat backend.tf
   ```
   (Adjust the path if you cloned the repo elsewhere.) A backend block cannot use variables, locals or data sources.

5. Migrate the state into S3:
   ```bash
   terraform init -no-color -migrate-state -force-copy
   ls terraform.tfstate* 2>/dev/null; aws s3 ls s3://$(cat ~/state_bucket) --recursive
   ```
   ```
   Successfully configured the backend "s3"! ...
   terraform.tfstate
   terraform.tfstate.backup
   2026-10-21 03:52:50       6216 hello/terraform.tfstate
   ```
   Terraform copied the state but left the old local files. S3 is now the source of truth, so delete the stale copies (they contain the same secrets):
   ```bash
   rm terraform.tfstate terraform.tfstate.backup
   ```

6. See locking stop a second writer: start one plan in the background, then a second one that refuses to wait:
   ```bash
   (terraform plan -no-color -lock-timeout=0s >/tmp/p1.txt 2>&1 &) ; sleep 2; terraform plan -no-color -lock-timeout=0s 2>&1 | tail -15; sleep 20; tail -3 /tmp/p1.txt
   ```
   The second plan fails (`Error acquiring the state lock`; the video's `tail` starts mid-message):
   ```
   Lock Info:
     Path:      allcs-tfstate-.../hello/terraform.tfstate
     Operation: OperationTypePlan
     Who:       cloudshell-user@...
     Version:   1.16.6
   ... you can disable locking with the "-lock=false" flag, but this is not recommended.
   ```
   The last lines come from the first plan, which held the lock and finished: `... no differences, so no changes are needed.`

7. Look at the bucket history:
   ```bash
   aws s3api list-object-versions --bucket $(cat ~/state_bucket) --prefix hello/ --query "Versions[].[Key,IsLatest,Size]" --output table
   ```
   ```
   |  hello/terraform.tfstate        |  True  |  6216  |
   |  hello/terraform.tfstate.tflock |  False |  273   |
   |  hello/terraform.tfstate.tflock |  False |  283   |
   ```
   The `.tflock` objects are locks taken and released (S3-native locking, GA in Terraform 1.11; DynamoDB locking is deprecated). Versioning is your undo button for a corrupted state.

8. Keep state out of git. Copy the `.gitignore` into your project and check it:
   ```bash
   cp ~/Devops_Course/terraform/m11-l03-state/.gitignore .
   git init -q 2>/dev/null; git check-ignore -v terraform.tfstate .terraform/ ; git status --short
   ```
   `*.tfstate` and `.terraform/` are ignored; `main.tf`, `backend.tf` and `.terraform.lock.hcl` are not.

### Commands to know (not run in the video)
| Need | Use |
|---|---|
| a crashed run left a lock | `terraform force-unlock <LOCK_ID>` - only your own lock, when automatic unlock failed |
| renamed a resource | `moved` block or `terraform state mv` (lesson 6) |
| forget a resource without deleting it | `terraform state rm` or a `removed` block |
| manage something built by hand | `import` block (lesson 6) |
| emergencies only | `terraform state pull` / `push` (push checks lineage and serial; `-force` skips that) |

## Common mistakes
- Committing `terraform.tfstate` to git: it holds secrets and git never forgets.
- Sharing state over chat or a shared drive: two copies, two truths, no locking.
- `-lock=false`: removes the only thing that stops two writers.
- Editing the JSON by hand: use `moved`, `state mv`, `state rm` and `import`.
- One giant state for everything: slow plans and a huge blast radius. Split per environment and component.
- An unencrypted, unversioned state bucket: turn on versioning, encryption and tight access before the first apply.

## Clean up
Lesson 6 continues with `~/tf/hello` and this state bucket; keep both if you continue. Otherwise, in this order:
```bash
cd ~/tf/hello && terraform destroy           # removes the media bucket (state is in S3)
bash ~/Devops_Course/terraform/m11-l03-state/delete-state-bucket.sh   # then the state bucket, all versions
```
Destroy first, while the state still exists; deleting the state bucket first would leave the media bucket unmanaged.
